# Phase 24 — The dataset: 100 labelled job postings

## 1. Goal

Every number Prompt Lab ever reports is only as good as this file. Build **100 hand-labelled job
postings** (minimum 50):
- varied on purpose and tagged, so the hard cases are visible;
- labelled against a written guide with a decision log;
- 20 double-checked by a second person through the `reviewer` role, with agreement measured by the
  **same scorer** the models face;
- anonymised so they can be published;
- split **30 dev / 70 test**, stratified by tag;
- stored in git as `cases/job-postings/data/job_postings.jsonl` in the **case-line format** the
  Playbook's importer reads (`playbook-contract.md` §2), and loaded into PostgreSQL by
  `import-cases.ts`.

This phase is mostly *your* work: collecting, reading, labelling. The code is small. Budget 6–8 hours,
and start labelling while you build Phases 10–18. It's the slow part.

## 2. What I will understand after this phase

1. What makes a test set representative, and why tags make the hard cases measurable.
2. Why labelling rules are written before labelling, and how a decision log keeps 100 labels
   consistent.
3. How to measure label quality (inter-annotator agreement) with the scorer itself, and what a low
   agreement on one field tells you.
4. What may be published from job postings, and how to anonymise without changing what's being
   tested.
5. Why the test split is stratified, and why you stop looking at it once it's made.

## 5. Concepts

**Variety on purpose.** Target mix for 100 postings. One posting usually carries several tags.

| Tag | ~Count | Covers |
| --- | --- | --- |
| `internship` | 25 | monthly stipends, "PPO", short durations |
| `full_time_in` | 25 | Indian full-time, CTC, LPA |
| `foreign` | 15 | USD/EUR/GBP, per hour or per year |
| `salary_lpa` | 20 | "3–5 LPA", "₹6L CTC", "up to 12 LPA" |
| `salary_hidden` | 15 | "competitive", "as per industry", "DOE" → `null` |
| `salary_hourly` | 8 | "$50/hr", "₹500 per hour" |
| `remote_ambiguous` | 20 | "WFH", "work from anywhere", "2 days in office", "remote (India only)" |
| `skills_buried` | 20 | skills inside paragraphs, not lists |
| `missing_fields` | 15 | no company (agency posts), no location, no experience |
| `hinglish` | 6 | mixed Hindi-English text ("fresher chalega", "WFH hai") |
| `messy` | 20 | emojis, bullets, HTML remnants, ALL CAPS |

The Playbook's Lesson 2 reads `salary_lpa` and `salary_hidden` by name. **Don't rename those two.**
Every tag must have **at least 3 test examples**, or its subset number is noise.

**Rules before labels, and a decision log.** Ambiguity is constant. Write every decision into
`LABELLING.md` the first time you meet it, then label consistently. Decisions to make up front (they
follow `scoring-rules.md` §2, which is binding):
- "MERN" → `mongodb, express, react, node.js` (stacks expand; add the synonyms the scorer needs to
  Phase 16's table, through a code change with a test, not a label hack);
- soft skills ("communication", "teamwork") are **not** skills;
- "fresher" / "0–1 years" → `experience_years_min: 0`; "1+ years" → 1; not stated → `null`;
- "₹6L CTC" → `{ min: 600000, max: 600000, currency: "INR", period: "year" }`;
- "up to ₹25k/month" → `{ min: null, max: 25000, currency: "INR", period: "month" }`;
- a city plus "remote option" → `hybrid` only if the posting names office days, otherwise `remote`;
- "competitive", "as per industry", "not disclosed" → salary `null`. This is the hallucination
  test: a model that invents a number scores 0.

These decisions go into the README's "How the test set was built".

**Drafting with a model is fine; trusting it isn't.** You may pre-fill a label with a model and only
correct it. But a benchmark graded against one candidate model's output is biased toward that model.
So: draft with a model **not** in the comparison (or none), check every field yourself, and record in
`SOURCES.md` how labels were produced.

**Agreement, measured by the scorer.** The second labeller is a workspace member with the `reviewer`
role (Phase 10). They label 20 postings (8 dev, 12 test) **without seeing your labels**: the label
editor hides `expected` from a reviewer while `secondLabel` is empty. `agreement.ts` scores their
labels against yours with `scoreFields()` from `@repo/scoring`, the exact function models face, and
writes per-field agreement to `AGREEMENT.md`. Disagreements are resolved into `expected`, the decision
goes into `LABELLING.md`, and the numbers go into the README. Low agreement on one field means the
**rule** is unclear. Fix the rule before blaming models.

**Sharing responsibly.** Job postings belong to the sites and companies that published them.
- Collect by hand from public postings, within each site's terms. No scraping that violates them.
- Publish an **anonymised, shortened** version: fictional company names from a fixed list, no emails,
  phone numbers, URLs or recruiter names, trimmed boilerplate. Keep everything that matters to the
  fields: the salary text, the work-mode wording, the skills sentences.
- **Anonymise first, then label the anonymised text**, so the label matches what's published
  (including the fictional company name).
- Where a posting can't be shared even anonymised, keep it out of the public file. The `Example` row
  gets `publicInput: false`, so published pages (Phase 22) show its id and fields, but not the input.
- `check-public.ts` is the gate: it fails on any `@`, `+91`, 10-digit run, `http`, `www.`, or a name
  from `cases/job-postings/.private-names.txt` (gitignored, your list of real company names seen).

**Stratified split, then hands off.** `stratified-split.ts` assigns `dev` / `test` per tag with a
fixed seed: every tag in both splits, about 30 / 70 overall. After that, **don't read test examples
while writing prompts**. Phase 19's editor greys out test inputs behind a "reveal" click that writes an
audit entry, so you can see later whether you peeked.

**Revisions.** Editing an `expected` after a run bumps `Example.revision`, and the run's
`datasetHash` (`sha256` of the `(ref, revision)` list) no longer matches the task's current hash. The
results page then shows "labels changed since this run". Old results stay comparable to each other,
not to new ones.

## 6. Steps

1. **Write `LABELLING.md`** from `scoring-rules.md` §2, plus the decision list above. About 1 hour.
2. **Collect 100 postings** into a private scratch file outside the repo, one block per posting, with
   the source noted. 2–3 hours. Aim for the tag mix.
3. **Anonymise** each one: fictional company names from a fixed list in `SOURCES.md`, contacts
   stripped. Add every real company name you replaced to `.private-names.txt`.
4. **Label** in a spreadsheet (one row per posting; one column per field, plus `tags` and `notes`) or
   in the web editor. Export the sheet as CSV.
5. **Convert and check:**
   ```bash
   pnpm --filter api exec tsx src/scripts/sheet-to-jsonl.ts --in ~/labels.csv \
     --task ../../cases/job-postings/task.json --out ../../cases/job-postings/data/job_postings.jsonl
   pnpm --filter api exec tsx src/scripts/check-public.ts ../../cases/job-postings/data/job_postings.jsonl
   ```
   `sheet-to-jsonl.ts` validates every `expected` against the task's field-rule schema
   (`@repo/types`) and refuses the file on the first invalid row, printing the row and the Zod path.
6. **Split** (writes `split` into each line; deterministic):
   ```bash
   pnpm --filter api exec tsx src/scripts/stratified-split.ts \
     ../../cases/job-postings/data/job_postings.jsonl --dev 30 --seed 20261103
   ```
7. **Import** into PostgreSQL:
   ```bash
   pnpm --filter api import-cases -- --case job-postings --dry-run
   pnpm --filter api import-cases -- --case job-postings
   ```
8. **Second labeller.** Invite them as `reviewer` (Phase 10). Pick the 20 with
   `stratified-split.ts --sample 20 --dev-share 0.4`; they label in the editor. Then:
   ```bash
   pnpm --filter api exec tsx src/scripts/agreement.ts --task job-postings \
     --export ../../cases/job-postings/data/second-label.jsonl \
     --report ../../cases/job-postings/data/AGREEMENT.md
   ```
9. **Resolve** each disagreement into `expected` (re-import), record the decision in `LABELLING.md`,
   and re-run `agreement.ts` so `AGREEMENT.md` shows before and after resolution.
10. **Commit** the public files.

**Weekend version:** 30 postings, all `dev`, no second labeller. Write exactly that in the README.

### `agreement.ts` (core)

```ts
import { scoreFields } from "@repo/scoring";
import { prisma, runAsSystem } from "../db/prisma";
import { Prisma } from "../generated/prisma/client";

// One row per field: share of the 20 where the second label scores 1 against the primary (skills: mean F1).
const rows = await runAsSystem(async () => {
  const task = await prisma.task.findFirstOrThrow({ where: { slug } });
  const examples = await prisma.example.findMany({
    where: { taskId: task.id, secondLabel: { not: Prisma.DbNull } },
  });
  const perField = new Map<string, number[]>();
  for (const ex of examples) {
    // Primary label is "expected", the second label plays the "model output".
    for (const f of scoreFields(task.fields, ex.secondLabel, ex.expected).fields) {
      perField.set(f.key, [...(perField.get(f.key) ?? []), f.score]);
    }
  }
  return { n: examples.length, perField };
});
```

The report writes `n`, each field's mean, and every disagreeing `(ref, field, primary, second)`, so the
discussion has a list to work through.

## 9. Interview angle

*"How did you build your test set?"* 100 real postings chosen to cover the hard cases: LPA salaries,
WFH variants, skills buried in prose, missing fields, Hinglish. Labelled against a written guide with
a decision log. A second person independently labelled 20 through a restricted reviewer account, and
I measured agreement with the same scorer the models face, so "the labels are good" is a number. They
were anonymised before labelling, split 30/70 stratified by tag, and I stopped reading the test split
once it was made. The editor even logs it if I reveal a test input.
